# AI Retail Analyst 面试演示脚本

> 面向「AI 大模型应用开发工程师」面试的现场演示指南。总时长建议 **6–8 分钟**。
> 本文档所有入口、问题、执行路径均以当前代码与真实运行结果为准，未虚构任何能力。

---

## 1. 演示目的与总时长

用一次连贯的现场操作，让面试官看到一条完整的「自然语言 → 工作流编排 → 真实工具/模型 → 结构化报告 → 校验与兜底 → 持久化 → 前端可视化」链路，而不是一个只会调 chat 接口的聊天机器人。

| 环节 | 时长 | 演示点 |
|---|---|---|
| 开场 + 环境确认 | 30s | 项目定位、已启动的服务 |
| 场景 A：宏观零售分析 | 1.5min | 数据查询 + ARIMA 预测 + 异常检测 |
| 场景 B：客户流失分析 | 1.5min | 模拟数据 + LightGBM + SHAP |
| 场景 C：综合分析报告（重点） | 2.5–3min | 意图路由 + 多工具 + 六段报告 + 字段核对 + 持久化 |
| 收尾总结 | 30s | 工程链路回顾 + 诚实边界 |

## 2. 演示前启动步骤与环境检查

### 2.1 确认服务已启动（避免重复占端口）



- 未配置 → Agent 自动降级为「模板兜底」，此时应把讲解重点放到 fallback 机制本身（见第 7 节）。


## 3. 开场讲解词（30 秒）

> “这是我做的一个零售数据分析 Agent 项目。核心想法是：用户用自然语言问一个经营问题，后端用一个 LangGraph 工作流先去识别意图、决定调用哪些工具，工具里跑的是真实数据查询和真实模型——宏观是 ARIMA 预测，用户侧是 LightGBM 流失预测加 SHAP 解释——然后把工具返回的真实结果交给 DeepSeek 生成一份六段式报告，最后再做一层字段核对、异常兜底和报告落库。前端是 Vue 3 + ECharts，把预测、风险分布和执行明细都画出来。我现在从头跑一遍给你看。”

## 4. 场景 A：宏观零售分析（约 1.5 分钟）

### 4.1 页面入口

首页 → 快捷场景卡片「**趋势预测**」（对应首页 `sales-forecast` 场景）。

### 4.2 可直接复制的演示问题

```
基于现有历史数据预测未来三个月社零走势，展示预测结果及模型评估信息。
```

### 4.3 操作与观察

1. 打开首页，右侧「经营脉搏」面板已实时显示：最新社零总额 **39,824.4 亿元（2026-08）**、同比增长、回测 MAPE。
2. 点击「趋势预测」卡片 → 页面进入加载态 → 下方出现「分析结果」。
3. 观察点：
   - 意图徽标显示「意图：宏观分析」；
   - 状态 pill 显示「AI 实时生成」；
   - 执行步骤依次为：**任务理解 → 知识检索 → 数据查询 → 趋势预测 → 报告生成**；
   - 图表区分「历史真实值（实线）」「未来预测值（虚线）」「95% 预测区间（浅色带）」「异常点（散点）」；
   - 下方「历史三个月回测对比」表格列出预测值 / 真实值 / 绝对误差 / 相对误差，并给出 ARIMA MAPE 与两个基线（沿用上月、同月去年）的 MAPE。

### 4.4 讲解词

> “场景 A 是宏观分析。这个问题命中‘宏观分析’意图，工作流只调用两个工具：`query_macro_sqlite` 从 SQLite 里查国家统计局的社会消费品零售总额月度数据，`forecast_timeseries` 用 statsmodels 的 ARIMA(1,1,1) 做预测。
> 这里我想强调口径：社零数据从 2012 年起是 1—2 月累计发布，所以 2 月当月值缺失。代码没有把累计值和单月值混在一起建模，也没有去补造 1—2 月的数据，而是显式剔除这些月份，回测窗口也校验日历连续性。
> 图上实线是历史真实值，虚线是未来 3 个月预测，浅色带是名义 95% 置信区间。下面这张回测表是我个人比较看重的地方——它不是只给一个预测数字，而是留出最近 3 个月，用更早的数据训练、逐月预测再和真实值对比，同时给了两个简单基线。这个窗口里 ARIMA 的 MAPE 是 4.36%，沿用上月基线是 4.08%，同月去年是 0.65%——也就是说在这个窗口 ARIMA 并没有明显优于同月去年基线，这个我会如实讲，不会把 4.36% 说成预测准确率。”

### 4.5 后端实现与关键技术点

| 关键点 | 位置 |
|---|---|
| 数据查询（单月口径过滤 + NaN/Inf 兜底） | `src/agents/tools.py` → `query_macro_sqlite` / `_finite_float` |
| ARIMA 预测 + 回测 + 异常检测 | `src/models/train_timeseries.py` → `run_forecast` |

## 5. 场景 B：客户流失风险分析（约 1.5 分钟）

### 5.1 页面入口（两个，选一个）

- 入口 1：首页快捷场景「**客户流失分析**」（`customer-churn`）。
- 入口 2：顶部导航「数据分析」→ Tab「用户流失预警」（更适合展示表格与 SHAP 图）。

### 5.2 可直接复制的演示问题

```
分析用户流失预测结果，展示风险分布、主要影响特征和需要注意的模型限制。
```

### 5.3 操作与观察

1. 首页点「客户流失分析」卡片 → 观察意图徽标为「意图：流失预测」，执行步骤只有：**任务理解 → 知识检索 → 流失预测 → 报告生成**（不会误调宏观工具）。
2. 切到「数据分析 → 用户流失预警」：
   - 顶部提示明确写「**以下用户与流失概率来自 LightGBM 模型对 RFM 模拟数据的真实批量推理；特征重要性为平均绝对 SHAP 值（模型解释指标，非百分比）**」；
   - KPI：预测样本数 **4766**、极高风险 **283**、高风险及以上 **959**、首要影响特征「最近购买天数」；
   - 「风险等级分布」柱状图 + 「特征重要性（SHAP）」横向条形图；
   - 下方「高流失风险用户明细」表格：用户 ID、最近购买天数、购买频次、流失概率、风险等级。

### 5.4 讲解词

> “场景 B 是流失分析，这里必须先声明边界：这 4766 个用户是 RFM 规则生成的**模拟数据**，不是真实企业客户，前端也一直在醒目的位置标着。模型是 LightGBM 二分类，特征包括 recency、frequency、monetary 和城市等级 one-hot，用 `scale_pos_weight` 处理正负样本不平衡。
> 表格里‘流失概率’是模型对单个用户输出的概率，比如最高的几个是 32.2%——这是**模型在模拟数据上的推理结果，不是真实业务流失率**。因为树模型会把不同特征组合落到同一个叶子，所以你会看到好几个用户概率相同，这是正常的。
> 右边那张图是 SHAP 的**平均绝对 SHAP 值**，它解释的是‘哪些特征对模型预测的贡献大’，单位不是百分比、也不等于流失概率。从图上能看出 recency_days 贡献最大，这符合直觉——最近一次购买时间离现在越远，流失风险越高。
> 风险等级不是拿 0.5 硬阈值切，而是按当前样本的概率分位数 P50/P80/P95 分成四档，避免阈值写死。这个推理接口是真实的，但结论只用来演示流程。”

### 5.5 后端实现与关键技术点

| 关键点 | 位置 |
|---|---|
| 批量推理（特征顺序取 `feature_names_in_`） | `src/models/churn_inference.py` → `predict_batch` |
| 风险分级（分位数 P50/P80/P95） | `churn_inference.py` → `assign_risk_levels` |
| SHAP 归因（TreeExplainer，降级到内置 importance） | `churn_inference.py` → `compute_feature_importance` |
| 流失工具（文本 + 结构化 payload） | `src/agents/tools.py` → `predict_churn_batch` |
| 前端表格与 SHAP 图 | `App.vue` → `loadChurn` / `renderFeatureChart` |

## 6. 场景 C：综合分析报告（重点，约 3 分钟）

### 6.1 页面入口

首页快捷场景「**经营报告生成**」（`business-report`），或顶部导航「AI Agent」页手输问题。

### 6.2 可直接复制的演示问题

```
结合宏观零售数据和用户流失情况，给出可执行的经营建议。
```

### 6.3 操作与观察

1. 首页点「经营报告生成」卡片 → 意图徽标显示「意图：综合分析」。
2. 执行步骤依次为：**任务理解 → 知识检索 → 数据查询 → 趋势预测 → 流失预测 → 报告生成**——这一步要强调「这是三个工具都被真实调用了，不是写死的文案」。
3. 观察报告正文的六段结构：
   - 【核心结论】 / 【数据依据】 / 【趋势与预测分析】 / 【异常与风险】 / 【建议的下一步分析】 / 【结果限制与不确定性】。
4. 点结果区的「在 AI Agent 中查看完整执行明细」按钮（或切到「AI Agent」导航）：
   - 「执行明细」折叠面板里能看到每一步的状态、耗时、**真实 SQL**、知识库来源、报告原文；
   - 「行动建议」卡片是结构化 JSON（title / rationale / evidence / priority）。
5. 后端侧验证持久化（见 6.6）。

### 6.4 讲解词

> “场景 C 是重点，它把前面两条链路组合起来。问题同时命中‘宏观’和‘流失’关键词，意图路由到‘综合分析’，工作流一次性调用三个工具：宏观查询、时序预测、流失批量推理，另外意图节点里还先跑了一次 RAG 知识检索。
> 我分三段讲清楚数据从哪来：数据库和模型只负责出**结构化的事实**——SQL 查出来的社零数字、ARIMA 的预测和回测、LightGBM 的概率和 SHAP；大模型只负责**组织语言**，系统提示词里强制它只能引用上下文里给的真实数字，缺数据要写‘暂无数据’，不许自己编。所以报告里每个数字都能追到工具输出。
> 生成完还有两层兜底。第一层是格式兜底：如果大模型输出缺了六段里的核心章节，直接降级成模板报告。第二层是字段核对：我们做了一个轻量的校验，数字锚点检查最新社零值、预测首值、样本总数有没有进报告；另外对高危用户的城市等级、年龄、流失概率按用户 ID 和工具结果逐字段比对——之前实测就抓到过模型把‘三线’写成‘二线’，抓到之后会在报告末尾追加一行‘字段核对提示’，给出权威值，而不是去全局替换字符串。
> 最后报告会通过 `report_store` 落到 SQLite 的 `analysis_reports` 表，每个报告一个 uuid 的 report_id，接口返回 `report_persisted` 标明有没有保存成功，保存失败也不影响报告本身返回。”

### 6.6 报告持久化如何现场验证（只读）

```bash
# 查看最近写入的报告（只读，不修改数据）
python -c "
import sqlite3
c = sqlite3.connect('retail.db')
for r in c.execute('SELECT id, intent, generation_status, substr(query,1,20) FROM analysis_reports ORDER BY created_at DESC LIMIT 3'):
    print(r)
c.close()
"
```

期望看到刚生成的那条记录：`id`（uuid 十六进制）、`intent='综合分析'`、`generation_status='success'`。

### 6.7 字段核对实际覆盖哪些字段（如实说明）

- **数字锚点（3 个）**：宏观最新社零值、预测首值、流失样本总数。
- **用户字段（高危 Top3）**：城市等级 `city_tier`、年龄 `age`、流失概率 `churn_prob`。
- **未覆盖**：`recency_days`/`frequency`/`monetary`/`risk_level` 未做自动核对；只能发现「报告出现且与工具结果不一致」的字段，无法发现模型编造的、工具结果里不存在的内容。这是**覆盖核对，不是完整事实核验**，讲解时不要拔高。

## 7. 常见异常及应对方法

| 异常现象 | 原因 | 应对（演示中直接说明） |
|---|---|---|
| 报告 pill 显示「AI 服务降级 · 模板兜底」 | `.env` 未配置/无效 API Key，或大模型超时、限流 | 正好演示 fallback：说明模板兜底只汇总真实工具结果，不做语义归纳；不要假装是 success |
| 分析请求返回 429 | 触发 `5 次/分钟/IP` 限流 | 等待 1 分钟再点；演示前避免反复点同一场景 |
| 首页「经营脉搏」显示「请启动后端服务」 | 后端未启动或端口不是 8003 | 检查 `curl /health`，确认后端在 8003 |
| 图表空白 | 前端加载时后端不可用 | 刷新页面；健康检查每 30s 会自动恢复在线状态 |
| 意图与预期不符 | 关键词落在规则兜底分支 | 用本文档提供的标准问题，命中「宏观/流失/综合」三类关键词 |

## 8. 演示中不能夸大的指标与功能边界

- **不是真实企业数据**：流失 4766 用户是 RFM 模拟数据，32.2% 是模型在模拟数据上的概率，不是真实流失率。
- **不是预测准确率**：MAPE 4.36% 只是「最近 3 个月留出回测」的相对误差，且该窗口 ARIMA 未明显优于同月去年基线；未来预测未经真实值验证。
- **SHAP 不是概率**：特征重要性是平均绝对 SHAP 值，单位不是百分比。
- **不是完整事实核验**：字段核对只覆盖有限字段（见 6.7）。
- **不是标准 MCP**：`MCPToolServer` 只是进程内普通 Python 方法，未实现 MCP 协议。
- **不是真实企业知识库**：RAG 检索的是 `docs/policy.txt` 示例研报文本，用字符级 n-gram TF-IDF。
- **不是 Text-to-SQL**：SQL 是代码里定义的业务查询，不是模型生成的。

## 9. 最后 30 秒总结

> “总结一下，这个项目我把它当作一条完整的工程链路在做，而不是一个 prompt 套壳：数据侧有采集和模拟数据生成；模型侧有 ARIMA 预测、LightGBM 流失和 SHAP 解释；服务侧是 FastAPI 暴露接口；编排侧是 LangGraph 做意图路由和工具调用；报告侧有六段式结构、字段核对和失败兜底；最后是 Vue 前端可视化，还有一套不调真实大模型就能跑的离线评测框架，总共 106 个后端测试。最想体现的是两点：一是每个数字都可追溯到工具输出，二是系统清楚地知道自己哪里不可靠——模型不可靠就用模板兜底、字段不可信就做核对提示，而不是假装什么都是对的。”
